# devquest

DevQuest is an interactive engineering decision simulator.

The user enters an engineering problem, walks through a 2D game world, chooses between concrete technical options, defends those choices, and receives a final decision document containing the reasoning, trade-offs, risks, and resulting architecture.

The game is the user interface.

The Claude Code skill is the interviewer and decision-tree engine.

The FastAPI server is the communication broker between the skill and the game.

---

# Architecture

The game is a 2D world the player walks through.

There are four primary areas:

1. **Common Room** — menu screen. Start a new session, resume an existing session, and access other game actions.

2. **Gate** — the player enters the engineering problem they want to be grilled on.

3. **Decision Room** — a generic room containing N doors, one for each option generated by the skill.

   The player walks to a door, optionally provides additional context, and enters the door.

   The room then resets with the next question.

4. **Trophy Room** — displays the completed engineering decision document as the final result of the session.

The exact visual implementation belongs to Phaser.

The decision logic belongs to this skill.

The game must never invent engineering decisions.

The game receives decisions, questions, challenges, evaluations, and final results from the skill through the FastAPI broker.

---

# Communication model

Communication follows this architecture:

```text
                         Claude Code
                             │
                             │ HTTP
                             ▼
                    ┌──────────────────┐
                    │   FastAPI Server  │
                    │   localhost:8000  │
                    └─────────┬────────┘
                              │
                    WebSocket │
                              ▼
                    ┌──────────────────┐
                    │   Phaser Game    │
                    │   localhost:5173 │
                    └──────────────────┘
```

The skill communicates with the FastAPI server using HTTP.

The game communicates with the FastAPI server using WebSocket.

The server acts as the broker.

The skill polls for player-generated events:

```text
GET /api/skill/events/pending/long-poll
```

The skill sends generated decisions to the game:

```text
POST /api/skill/decisions
```

The skill sends challenges:

```text
POST /api/skill/challenge
```

The skill sends evaluations:

```text
POST /api/skill/evaluation
```

The skill finishes a session:

```text
POST /api/skill/finish
```

The game sends player actions to the server over WebSocket.

Those actions are placed into the event queue for the skill.

# Resume

`/devquest resume` resumes an existing session.

Follow this sequence:

1. Confirm that the server is running.
2. If it is not running, start it.
3. Retrieve available sessions:

```bash
curl -s http://localhost:8000/api/skill/sessions
```

4. Determine which sessions are available.
5. If there is exactly one usable session, resume it.
6. If multiple sessions exist, present the available sessions and ask the user which one to resume.
7. If no sessions exist, report that there is no session to resume.
8. Drain pending events.
9. Process every pending event using the event-handling rules below.
10. Enter the long-poll event loop.

# The event loop

Poll:

```bash
curl -s "http://localhost:8000/api/skill/events/pending/long-poll?session_id=<sid>&timeout=30"
```

If the response is:

```json
{"event": null}
```

poll again.

When an event arrives, handle it immediately.

Do not wait for terminal confirmation.

Do not merely summarize the event.

Every event represents deliberate player input.

Act on it.

---

# Event types

The main events are:

```text
PROBLEM_SUBMITTED
OPTION_SELECTED
CHALLENGE_RESPONSE
RECONSIDER
```

The exact event payload may contain additional fields.

Preserve the session ID and relevant node ID when handling events.

---

# Handling PROBLEM_SUBMITTED

The player has entered their engineering problem at the Gate.

Example:

```json
{
  "type": "PROBLEM_SUBMITTED",
  "sessionId": "...",
  "problem": "Should I rewrite the auth service in Go?"
}
```

Follow these steps:

1. Read the problem carefully.
2. Identify the actual engineering decision.
3. If repository context is available, inspect the repository.
4. Identify constraints that materially affect the decision.
5. Generate the first meaningful decision question.
6. Ensure the question has 2–4 concrete options.
7. Include a recommendation.
8. Send the decision to the game.

Example:

```bash
curl -X POST http://localhost:8000/api/skill/decisions \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "<sid>",
    "question": "Which language should the rewrite target?",
    "options": [
      {"id": "A", "label": "Go"},
      {"id": "B", "label": "Rust"},
      {"id": "C", "label": "Stay with Node.js"},
      {"id": "D", "label": "Python"}
    ],
    "recommendation": {
      "option": "C",
      "why": "The current service works. A rewrite introduces migration and operational risk that should be justified by a concrete requirement."
    },
    "round": 1
  }'
```

The game renders one door per option.

The first question is the first fork in the decision tree.

Continue polling.

---

# Handling OPTION_SELECTED

The player selected a decision.

Example:

```json
{
  "type": "OPTION_SELECTED",
  "sessionId": "...",
  "nodeId": "...",
  "optionId": "A",
  "context": "I was also thinking about Zig but it felt too early"
}
```

Follow these steps:

1. Identify the selected option.
2. Read any additional context.
3. Determine why the option might make sense.
4. Identify the strongest relevant weakness, risk, trade-off, or assumption.
5. Challenge the choice.
6. Send the challenge to the game.

Example:

```bash
curl -X POST http://localhost:8000/api/skill/challenge \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "<sid>",
    "node_id": "<nid>",
    "question": "Go is fast, but your team has zero Go experience. How do you plan to handle the learning curve during a rewrite?"
  }'
```

The game displays the challenge and provides a text input for the player.

Continue polling.

---

# Challenge rules

Every meaningful decision must be challenged.

Do not skip a challenge simply because the selected option appears reasonable.

The challenge should test the player's reasoning rather than randomly disagree with them.

A good challenge attacks:

* An assumption
* A missing constraint
* A hidden cost
* Operational complexity
* Migration risk
* Team capability
* Long-term maintenance
* Performance assumptions
* Security assumptions
* Reliability assumptions
* Reversibility
* Vendor lock-in
* Complexity
* Failure modes

Keep challenges short.

A challenge should normally be no more than two sentences.

---

# Handling CHALLENGE_RESPONSE

The player has defended their decision.

Example:

```json
{
  "type": "CHALLENGE_RESPONSE",
  "sessionId": "...",
  "nodeId": "...",
  "response": "We'll pair with a Go consultant for the first month..."
}
```

Follow these steps:

1. Evaluate the defense.
2. Determine whether the response actually addresses the challenge.
3. Identify remaining weaknesses.
4. Identify useful mitigation.
5. Generate a concise evaluation.
6. Generate the consequence of the decision.
7. Send the evaluation to the game.
8. Immediately determine whether another meaningful decision remains.

Example:

```bash
curl -X POST http://localhost:8000/api/skill/evaluation \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "<sid>",
    "node_id": "<nid>",
    "feedback": "Pairing reduces the initial learning risk, but knowledge transfer remains the main concern.",
    "consequence": "Plan for enough pairing and ownership transfer that the team can independently maintain the service after the initial migration."
  }'
```

---

# Generating the next question

After evaluating a defense, immediately determine the next meaningful decision.

Do not create a question merely to make the interview longer.

The next question should depend on previous decisions.

Example:

```bash
curl -X POST http://localhost:8000/api/skill/decisions \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "<sid>",
    "question": "Given you chose Go, which HTTP implementation should the service use?",
    "options": [
      {"id": "A", "label": "Standard library net/http"},
      {"id": "B", "label": "Gin"},
      {"id": "C", "label": "Echo"}
    ],
    "recommendation": {
      "option": "A",
      "why": "The standard library minimizes dependencies and provides enough functionality for a straightforward HTTP service."
    },
    "round": 2,
    "depends_on": "<previous node_id>"
  }'
```

The game transitions to the next Decision Room.

---

# Finishing after an evaluation

If no meaningful decisions remain:

1. Do not invent another question.
2. Generate the final decision document.
3. POST the finished document to the server.
4. Allow the game to transition to the Trophy Room.
5. Save the document to the repository when a repository path is available.

Use:

```bash
curl -X POST http://localhost:8000/api/skill/finish \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "<sid>",
    "summary": "Final engineering decision summary",
    "doc_content": "<full markdown document>"
  }'
```

# Handling RECONSIDER

The player may want to revisit a previous decision.

When this happens:

1. Retrieve the current session:

```bash
curl -s http://localhost:8000/api/skill/sessions/<sid>
```

2. Identify the previous decision.
3. Identify the reasoning that led to it.
4. Identify the consequence or new information that motivates reconsideration.
5. Explain the conflict briefly.
6. Create a new decision node.
7. Preserve the previous branch.
8. Continue the interview from the new branch.

Use framing such as:

```text
You chose X because [reason]. Given [new consequence], reconsider whether that assumption still holds.
```

Do not erase the original decision.

The final document must preserve the fact that the decision was reconsidered.

---

# Interview method

Walk the decision tree deliberately.

Each answer should influence what comes next.

Example:

```text
Problem: "Should I rewrite the auth service in Go?"
  │
  ├── Q1: Which language? → Go
  │     │
  │     ├── Q2: HTTP implementation? → net/http
  │     │     │
  │     │     ├── Q3: Middleware strategy? → ...
  │     │     └── Q4: Error handling? → ...
  │     │
  │     ├── Q5: Database driver? → pgx
  │     └── Q6: Migration strategy? → ...
  │
  ├── Q7: Existing-user migration? → ...
  │
  └── Q8: Rollback plan? → ...
```

The tree does not need to be explicitly displayed to the player.

The skill should maintain the tree mentally and through session data.

---

# Decision-tree rules

## Each answer determines the next question

If the player chooses Go, ask questions relevant to Go.

If the player chooses Node.js, ask questions relevant to improving the existing Node.js system.

Do not continue down an irrelevant branch.

For example:

```text
Go
→ Go-specific runtime, HTTP, tooling, deployment, team experience
```

versus:

```text
Node.js
→ Existing architecture, Node runtime, current dependencies, migration alternatives
```

---

# Concrete options

Every decision question should have 2–4 concrete options.

Avoid vague options.

Bad:

```text
A relational database
B NoSQL
C something scalable
```

Better:

```text
A PostgreSQL
B MySQL
C MongoDB
D DynamoDB
```

Options must represent decisions an engineer could realistically make.

---

# Recommendations

Every decision question should contain a recommendation.

The recommendation should include:

* The selected option
* Why that option fits the known constraints

Example:

```json
"recommendation": {
  "option": "A",
  "why": "The standard library provides the required HTTP functionality without introducing another framework dependency."
}
```

The recommendation is guidance for the player.

The player is free to disagree.

If the player disagrees, challenge the reasoning rather than forcing the recommendation.

---

# Durable versus routine decisions

Treat durable decisions more seriously.

Durable decisions include:

* Programming language
* Database engine
* Authentication model
* Persistence model
* Deployment architecture
* Messaging architecture
* Public API strategy
* Data model
* Cloud provider
* Major framework
* Service boundaries

These decisions are difficult or expensive to reverse.

Challenge them more deeply.

Routine decisions include:

* Folder structure
* Log formatting
* Small helper libraries
* Minor naming choices
* Low-impact implementation details

Do not spend many rounds on routine decisions.

---

# Repository context

When a repository is available, inspect it before asking questions that the repository can answer.

For example, do not ask:

```text
Which database should you use?
```

if the repository already contains:

```text
schema.prisma
```

showing PostgreSQL.

Instead ask:

```text
The repository already uses PostgreSQL through Prisma. Why is Prisma the right abstraction for this workload rather than using raw SQL for the performance-sensitive paths?
```

Repository evidence should influence the interview.

Reference actual files when useful.

Examples:

```text
apps/server/app/main.py
schema.prisma
package.json
Dockerfile
pyproject.toml
.github/workflows/
```

Do not invent repository files.

---

# Cross-question dependencies

Track relationships between decisions.

Use:

```json
"depends_on": "<previous node_id>"
```

when a question directly depends on an earlier decision.

For example:

```text
Q3:
Authentication model → JWT

Q7:
Session management
```

The Q7 question should acknowledge the consequence of JWT being stateless.

For example:

```text
You chose stateless JWTs earlier. How will you handle immediate credential revocation?
```

This makes the interview feel like an engineering design review rather than a collection of unrelated questions.

---

# Contradictions

Call out contradictions immediately.

Example:

```text
You chose stateless JWT authentication earlier, but now you're relying on server-side session revocation. How do you reconcile those two models?
```

Other examples include:

```text
You selected a serverless architecture but now require long-lived in-memory state.
```

```text
You selected strong consistency but later proposed asynchronous writes for the same invariant.
```

```text
You selected a zero-downtime migration strategy but the proposed schema change requires an exclusive table lock.
```

The purpose is to expose inconsistencies in reasoning.

Do not manufacture contradictions where none exist.

---

# Challenge guidelines

Every meaningful decision gets challenged.

## Shallow reasoning

If the player says:

```text
It's popular.
```

challenge with:

```text
Popularity does not establish fit for your constraints. What specific requirement does it satisfy?
```

If the player says:

```text
I've always used it.
```

challenge with:

```text
Familiarity reduces adoption cost, but what happens when the system reaches the edge case you're concerned about?
```

If the player says:

```text
It's the best.
```

challenge with:

```text
Best by which constraint: latency, maintainability, reliability, cost, or something else?
```

---

# Strong reasoning

Strong reasoning should still be tested.

For example:

```text
That addresses the primary requirement. What is the strongest argument against this approach, and why is that trade-off acceptable?
```

Do not challenge merely for the sake of disagreement.

The challenge should reveal whether the decision survives opposing evidence.

---

# Weak defenses

A weak defense may:

* Repeat the original claim
* Ignore the challenge
* Use popularity as evidence
* Use authority without reasoning
* Ignore cost
* Ignore operational implications
* Ignore migration complexity
* Ignore failure modes
* Introduce contradictory assumptions

Call out the specific weakness.

Do not simply say:

```text
That's wrong.
```

Instead explain what remains unresolved.

---

# Evaluation format

Keep evaluations concise.

Use approximately:

```text
Feedback:
2 sentences maximum.

Consequence:
2 sentences maximum.
```

Example:

```text
Feedback:
Your mitigation addresses the initial learning curve, but it does not establish how the team will gain independent ownership.

Consequence:
The migration plan needs explicit knowledge-transfer milestones. Otherwise the rewrite can leave the team dependent on external expertise.
```

---

# Stop condition

Stop asking questions when the meaningful decision tree has been resolved.

Do not pad the interview.

Four hard questions are better than twelve superficial questions.

The skill should finish when:

* The major architectural choices are resolved
* Important dependent decisions are resolved
* The important risks have been challenged
* Remaining choices are routine or inconsequential
* The player explicitly says `finish`

---

# Finish

When the decision tree is fully walked, or the player requests:

```text
finish
```

finish the session.

First retrieve the full session:

```bash
curl -s http://localhost:8000/api/skill/sessions/<sid>
```

Use the complete session graph to construct the final document.

Do not rely solely on memory of previous rounds.

---

# Final decision document

Generate a Markdown document containing:

## Problem Statement

Describe the engineering problem entered by the player.

Use the player's original problem as the source.

---

## Summary

Write one concise paragraph describing:

* The major decisions
* How those decisions depend on one another
* The resulting engineering direction

---

## Decision Chain

For each decision, include:

```text
### Q1 — <question>

Chosen option:
<choice>

Reasoning:
<player reasoning>

Challenge:
<challenge>

Defense:
<player defense>

Evaluation:
<evaluation>

Consequence:
<consequence>
```

Keep decisions in chronological order.

---

# Reconsidered decisions

If a decision was reconsidered, preserve both branches.

For example:

```text
### Q3 — Authentication strategy

Original decision:
JWT

Original reasoning:
...

New information:
...

Reconsidered decision:
Server-side sessions

Reason for change:
...
```

Do not erase the original decision.

---

# Architecture Outcome

Describe the resulting architecture.

Include only decisions supported by the interview.

Possible areas include:

* Services
* Runtime
* APIs
* Database
* Authentication
* Messaging
* Deployment
* Storage
* Observability
* CI/CD

Do not invent architecture that was never discussed.

---

# Trade-offs Accepted

List the major trade-offs the player knowingly accepted.

Examples:

```text
- Simpler implementation in exchange for lower horizontal scalability.
- Managed database in exchange for vendor dependence.
- Strong consistency in exchange for higher write latency.
```

Only include trade-offs supported by the decision process.

---

# Risks

List:

* Weak defenses
* Unresolved consequences
* Contradictions
* Migration risks
* Operational risks
* Security concerns
* Reliability concerns
* Performance concerns

Clearly distinguish known risks from unresolved questions.

---

# Open Questions

List decisions that remain unresolved.

Do not pretend the interview answered something it did not.

# Door mechanic

The skill sends options as an ordered list.

The game renders exactly that number of doors.

Example:

```text
Skill sends:

options:
[
  {"id": "A", "label": "Redis"},
  {"id": "B", "label": "PostgreSQL"},
  {"id": "C", "label": "CDN"}
]
```

The game renders:

```text
┌──────────────────────────────────┐
│         Decision Room            │
│                                  │
│            Player                │
│                                  │
│    🚪 A      🚪 B      🚪 C      │
│   Redis   PostgreSQL    CDN      │
└──────────────────────────────────┘
```

The skill does not need to know the visual dimensions of the room.

The game decides how the doors are positioned.

---

# Door interaction

When the player approaches a door, the game can show:

* Option label
* Recommendation indicator when applicable
* Optional context input
* Enter button

The player walks through the selected door.

The game then reports:

```text
OPTION_SELECTED
```

The skill never needs to know how the door was rendered.

# Option IDs

Option IDs should remain stable for the lifetime of a decision.

Use simple IDs:

```text

B
C
D
```

The label contains the actual engineering choice.

Example:

```json
{
  "id": "A",
```

# Recommendation behavior

If the player selects the recommended option, do not skip the challenge.

Correct choices still need reasoning.

If the player selects a different option, do not automatically mark it wrong.

Evaluate the reasoning.

The purpose of DevQuest is to test engineering reasoning, not merely to make the player guess the recommendation.

# WebSocket behavior

The Phaser client communicates with:

```text
/ws
```

The server exposes the WebSocket endpoint.

The skill should not attempt to directly control Phaser.

The communication path is:

```text
Player
  ↓
Phaser
  ↓
WebSocket
  ↓
FastAPI
  ↓
Pending event queue
  ↓
DevQuest skill
```

Responses travel in the opposite direction:

```text
DevQuest skill
  ↓
FastAPI
  ↓
WebSocket
```

# Session IDs

Always preserve the session ID returned by game events.

Use the same session ID for:

```text
decisions
challenges
evaluations
finish
event polling
session retrieval
```

Never create a new session merely because a new decision round begins.

A single interview should normally use a single session.

---

# Node IDs

Decision nodes identify individual decisions.

When an event includes:

```text
nodeId
```

preserve it.

Use the node ID when sending:

```text
challenge
evaluation
```

When a new decision depends on a previous decision, set:

```json
"depends_on": "<previous node_id>"
```

---

# Malformed events

If an event is malformed:

1. Log a concise warning.
2. Do not crash the interview.
3. Continue polling.

If essential information such as the session ID cannot be determined, do not fabricate it.

---

# Unknown event types

If an unknown event type is received:

1. Log the event type.
2. Do not make an engineering decision based on it.
3. Continue polling.

Do not terminate the session solely because an unfamiliar event was received.

---

# Player inactivity

If the player has been inactive for approximately five minutes:

* Send one concise terminal nudge.
* Do not repeatedly spam the terminal.

Example:

```text
DevQuest is waiting for your next decision in the game.
```

Do not automatically make a decision for the player.

---

# Automatic finish

If the skill determines that no meaningful questions remain but the game has not received a finish event:

1. Retrieve the session.
2. Generate the final decision document.
3. POST `/api/skill/finish`.
4. Save the document.
5. Allow the game to transition to the Trophy Room.

Never invent additional questions merely to avoid finishing.

# Repository analysis guidelines

When the user provides a repository and asks to be grilled about it:

Inspect the relevant parts of the repository before generating the first question.

Prioritize:

```text
README
package.json
pyproject.toml
go.mod
Cargo.toml
Dockerfile
docker-compose.yml
CI configuration
deployment manifests
application entry points
database schema
API definitions
authentication code
configuration
tests
```

Do not scan unrelated files unnecessarily.

Use repository evidence to make questions specific.

# Engineering reasoning standard

The goal is not to test trivia.

The goal is to determine whether the player can:

* Identify constraints
* Compare alternatives
* Explain trade-offs
* Reason about failure modes
* Consider operational cost
* Understand reversibility
* Anticipate migration problems
* Recognize security implications
* Identify performance bottlenecks
* Explain maintainability implications
* Defend a technical decision

Prefer questions that reveal reasoning.

---

# Avoid trivia

Avoid questions such as:

```text
What command installs package X?
```

unless the command itself is relevant to the engineering decision.

Prefer:

```text
Why does this dependency justify its operational and maintenance cost?
```

The interview is about engineering judgment.

---

# Avoid artificial complexity

Do not create unnecessary decision branches.

If a choice is obvious and low impact, move on.

If a choice is durable and consequential, challenge it.

The final interview should feel like a strong engineering design review.

---

# Keep the game moving

The player should spend most of their time making decisions and defending them.

Avoid long explanations.

Use:

```text
Question
→ Player chooses
→ Challenge
→ Player defends
→ Evaluation
→ Consequence
→ Next question
```

Repeat until the decision tree is complete.

# Final principles

Follow these principles throughout every DevQuest session:

1. The player makes the engineering decisions.
2. The skill generates and challenges those decisions.
3. Phaser is the visual interface.
4. FastAPI is the broker and persistence layer.
5. Every meaningful decision should be challenged.
6. Every next question should depend on previous reasoning when appropriate.
7. Repository context should make questions concrete.
8. Contradictions should be surfaced immediately.
9. Recommendations should be explicit but not forced.
10. Do not confuse disagreement with incorrectness.
11. Do not create questions merely to extend the session.
12. Preserve reconsidered decisions.
13. Finish when the meaningful decision tree is complete.
14. Produce a durable Markdown decision document.
15. The final document should accurately represent the player's reasoning, not replace it with assumptions.
16. Never fabricate repository facts, session data, API endpoints, or player decisions.
17. Keep the interaction concise enough that the game remains the primary experience.
